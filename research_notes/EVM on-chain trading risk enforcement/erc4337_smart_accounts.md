# ERC-4337 Account Abstraction & Smart Accounts for On-Chain Trading Risk Enforcement

## How does ERC-4337's validation phase and execution phase work mechanically, and where would a risk-rule check live (smart account logic, ERC-6900/ERC-7579 module, or elsewhere)? Can it revert/block an operation before it reaches the target contract?

### Takeaway
ERC-4337 processes a UserOperation in two strictly separated phases via the singleton EntryPoint contract — validation (`validateUserOp`) then execution — and the EntryPoint validates every op in a bundle before executing any of them; a risk-rule check can live in the smart account's own validation logic, in a pluggable validator/hook module (ERC-6900 or ERC-7579), or as a Safe-style pre/post-execution Guard, and in all cases it can revert and fully block the operation from ever reaching the target contract.

### Cited Findings
- When a bundler submits UserOperations to `handleOps()` on the EntryPoint, processing occurs in two phases: the EntryPoint calls `validateUserOp()` on the sender's smart account to verify validity (e.g., signature, ability to pay gas), then — only if validation passes — the EntryPoint calls back into the smart account to execute the actual `callData` (the real operation: transfer, swap, contract call, batch) — [HackerNoon: ERC-4337 Guide Part 1 (EntryPoint)](https://hackernoon.com/a-developers-guide-to-building-next-gen-smart-wallets-with-erc-4337-part-1-the-entrypoint); [Eco: ERC-4337 Explained](https://eco.com/support/en/articles/14797811-erc-4337-explained-account-abstraction)
- Validation must complete within strict gas limits and can only access predefined/allowed storage slots, which protects bundlers from unbounded gas consumption or state that could change before execution — [Eco: ERC-4337 Explained](https://eco.com/support/en/articles/14797811-erc-4337-explained-account-abstraction)
- The EntryPoint validates every UserOperation in a bundle before executing any of them (validate-then-execute across the whole bundle); writing state during `validateUserOp` and relying on it during execution is dangerous because another op's validation in the same bundle can overwrite it before execution runs — [Trail of Bits: Six mistakes in ERC-4337 smart accounts](https://blog.trailofbits.com/2026/03/11/six-mistakes-in-erc-4337-smart-accounts/)
- ERC-7579 (minimal modular smart accounts) defines four module types attachable to a wallet: **Validators** (authentication for transactions, i.e., logic callable from `validateUserOp`), **Executors** (execute actions on behalf of the account), **Hooks** (intercept and can modify/block transaction flow before and/or after execution), and **Fallback Handlers** (handle unknown function calls) — [ERC-7579 Modules listing](https://erc7579.com/modules); [Eco: ERC-7579 Explained](https://eco.com/support/en/articles/11890018-erc-7579-the-modular-smart-account-standard-explained)
- Hooks "run code before and after each transaction, see the full call data and can revert if a policy fails" — spending limits, transaction whitelists, and rate limiters all fit this hook pattern; a common configuration installs a session-key validator (who can sign) alongside a spending-limit hook (hard daily cap enforcement) for defense-in-depth — [Eco: ERC-7579 modular accounts](https://eco.com/support/en/articles/11890018-erc-7579-the-complete-guide-to-modular-smart-accounts)
- Separately from ERC-4337/7579, Safe's **Guard** pattern works at the base-account level (not AA-specific): a Guard contract is called by the Safe both before (`checkTransaction`) and after (`checkAfterExecution`) every `execTransaction`, and if `checkTransaction` reverts, the whole `execTransaction` reverts too — i.e., the Guard can fully block a transaction pre-execution, or flag/fail on final state post-execution — [Safe docs: Building a Guard tutorial](https://docs.safe.global/advanced/smart-account-guards/smart-account-guard-tutorial); [Ackee Blockchain: A Safe-native Solution to the Bybit Hack](https://ackee.xyz/blog/a-safe-native-solution-to-the-bybit-hack/)
- Safe v1.5.0 introduced **module guards**, an on-chain rule layer that filters every module call before execution, closing a prior gap where modules could bypass ordinary transaction Guards — Safe owners can now set a module guard alongside the regular guard to enforce global security rules even for module-initiated transactions — [Safe Foundation: Introducing Safe v1.5.0](https://safefoundation.org/blog/introducing-safe-v1-5-0-module-guards-enhanced-smart-account-features)

### Inferences
- For a trading-risk use case, the most natural placement is a **hook/guard that runs on every execution path** (not only a validator), because validators primarily gate *who* can authorize an op (signature/session-key checks under gas/storage restrictions), while hooks/guards see the actual call data and resulting state and can enforce substantive limits (position size, leverage, cumulative loss) with full revert power both pre- and post-execution.
- Because ERC-4337 validates an entire bundle before executing any op, any risk logic that depends on sequencing within a single bundle (e.g., "block the 3rd trade of the day") must be enforced in the execution-phase hook/module, not purely in `validateUserOp`, to avoid the documented storage-read-before-write hazard across ops in the same bundle.
- A hook-based implementation generalizes across ERC-7579-compliant accounts (Safe's AA module, Biconomy Nexus, ZeroDev Kernel), while a Safe Guard is specific to Safe's own non-AA `execTransaction` path — meaning a given "risk rule contract" may need two different wrapper interfaces (ERC-7579 hook vs. Safe Guard ABI) to work across both ecosystems, even though the underlying revert-based enforcement logic can be shared.

### Gaps
- Exact ERC-4337 storage-access restriction rules (which slots a validator may read during `validateUserOp`) were not retrieved in detail from the EIP-4337 spec itself — only secondary summaries were reviewed. The precise list of "allowed storage" rules relevant to building a compliant on-chain risk-check validator was not independently confirmed from the primary EIP text in this pass.
- ERC-6900 (Alchemy's original modular account standard) module-type terminology (e.g., its specific hook/validation function hooks) was not directly fetched from the ERC-6900 spec; findings on Alchemy's module architecture come from Alchemy's own product docs, which describe "plugins" rather than the ERC-6900 spec text directly.

## Platform comparison: Safe{Core} AA module, Biconomy, ZeroDev Kernel, and Alchemy Modular Account — do they ship spending-limit / session-key-with-constraints modules, and what exact constraints can they express (USD value, contract address, time window, cumulative count)?

### Takeaway
All four platforms ship production, shipped (not just roadmap) session-key/permission systems that can constrain by token amount (native or ERC-20, not direct USD), target contract/function, and time window; cumulative/count-based limits exist in varying maturity — Alchemy's Session Key Plugin explicitly supports spend limits "within an interval or in total," Biconomy/ZeroDev's policy systems support value limits and (per ERC-7579 "Smart Sessions") usage-limit/rate-limit policies, while none of the fetched docs show a native "USD-denominated" limit (all are token-amount based, requiring an oracle/hook to convert to USD).

### Cited Findings
- **ZeroDev Kernel** (v2, EntryPoint 0.6) session keys support: `validUntil`/`validAfter` (time window), `valueLimit` (max value transmitted, apparently per transaction), target contract restriction (specific address or wildcard "zeroAddress" matching an ABI), function-level argument validation using comparison operators (EQUAL, GREATER_THAN, LESS_THAN, etc.), and optional restriction to specific paymasters — [ZeroDev docs: Session Keys](https://docs.zerodev.app/smart-accounts/permissions/session-keys)
- ZeroDev Kernel v4 generalizes this into **"permissions"**: a composition of one signer plus one or more policies; policies enforce rules such as spending limits and target allowlists, letting a dapp receive a signer restricted to specific call selectors under specific policies (spending caps, time windows, target restrictions) without touching the root validator — [ZeroDev docs: Sudo Policy](https://docs.zerodev.app/sdk/permissions/policies/sudo); [ZeroDev docs: Signature Caller Policy](https://docs.zerodev.app/smart-accounts/permissions/policies/signature)
- The ERC-7579 ecosystem's **"Smart Sessions" validator module** (referenced via erc7579.com/Rhinestone tooling) exposes multiple composable policy types: Spending Limits Policy (restricts token transfer amounts), Time Frame Policy (constrains execution to specific periods), Usage Limit Policy (caps transaction frequency/count), Value Limit Policy (monetary thresholds), Universal Action Policy (defines which contracts/functions are callable), a Sudo Policy (bypasses all other policies for an admin key), and a Rate Limit Policy (limits number of transactions in a given time period) — [ERC-7579 Modules](https://erc7579.com/modules)
- **Biconomy** ships an ERC-4337 stack built around **Nexus**, an ERC-7579-compliant modular smart account, plus a **Session Key Manager Validation Module** that checks whether a given UserOperation adheres to the permissions defined for the session key and that it was signed by that session key; Biconomy's **Smart Session policies** govern "which contract functions can be called, what parameters are allowed, how much value can be transferred, when the permissions are valid, and which blockchain networks are authorized" — [Biconomy docs: Execute Transactions on Users' Behalf](https://docs.biconomy.io/new/smart-sessions/execute-transactions-on-users-behalf); [Biconomy docs: Smart Session Policies](https://docs.biconomy.io/new/smart-sessions/policies); [Eco: Best Smart Wallet SDKs for Developers (2026)](https://eco.com/support/en/articles/14797815-best-smart-wallet-sdks-for-developers-2026)
- Because Nexus targets the ERC-7579 spec, "modules written for Nexus are portable to other 7579-compliant accounts" — meaning a risk-policy module built once (e.g., Rhinestone's Smart Sessions) can in principle be reused across Biconomy, ZeroDev Kernel (v4+, which is also moving toward 7579 compatibility per ecosystem docs), and other 7579 accounts — [Eco: Best Smart Wallet SDKs for Developers (2026)](https://eco.com/support/en/articles/14797815-best-smart-wallet-sdks-for-developers-2026)
- **Alchemy's Session Key Plugin** (an ERC-6900 modular plugin for its Modular Account) supports: start/end times per key (time window), access-control lists to allow/deny target addresses, a requirement to use specific paymasters, and **spending limits for ERC-20 tokens, native tokens (ETH/MATIC), and gas**, each either as a **total-for-the-key cap or a cap that refreshes on a configurable interval** — explicitly supporting both cumulative-total and periodic/rolling limit semantics — [Alchemy: Session Key Plugin](https://www.alchemy.com/dapps/session-key-plugin)
- Alchemy's **Modular Account V2** delivers 40%+ reduced gas costs versus earlier modular account designs through optimization — [Alchemy: Session Key Plugin](https://www.alchemy.com/dapps/session-key-plugin)
- On the Safe side (not ERC-4337-native but composable via Safe's own AA module), the **Safe Allowance Module** lets a designated address spend up to a configured amount **per period** — a recurring/periodic daily-style allowance rather than an absolute lifetime cap — [Eco: Safe Wallet Deep Dive 2026](https://eco.com/support/en/articles/15254042-safe-wallet-deep-dive-2026-multisig-and-smart-accounts); [Remix (X/Twitter)](https://x.com/EthereumRemix/status/2024424369032716551)

### Inferences
- None of the fetched module systems natively express limits in USD; all operate on token-denominated amounts (ETH/native, specific ERC-20 units) or transaction/call counts. A USD-denominated "max daily loss" or "max position size" rule would require either (a) restricting trades to a single stable-valued asset so token amount ≈ USD, or (b) a custom hook/policy module that pulls a price oracle and converts on-chain before comparing against a USD threshold — this is architecturally straightforward (hooks can call out to other contracts) but not something any platform ships out-of-the-box per the docs reviewed.
- "Max trade count" (a pure count-based constraint, independent of value) maps most directly onto the Usage Limit Policy / Rate Limit Policy concepts in the ERC-7579 Smart Sessions ecosystem and is not something Alchemy's or ZeroDev v2's documented session-key constraints explicitly name (Alchemy's "interval" limits are value/gas based, not a raw call-count cap) — a custom policy or hook would likely be needed for an exact "max N trades per day" rule unless the Rate Limit Policy module directly supports it (this needs verification against the Rhinestone/Smart Sessions reference implementation directly).
- "Max leverage" and "max position size" as margin/derivatives-specific concepts are not primitives in any of these AA module systems — they are protocol-specific state (e.g., a perp DEX's internal position accounting), so enforcing them on-chain at the account layer would require a hook that reads the target protocol's state (e.g., via a view call to the perp contract) post-trade and reverts if the resulting position/leverage exceeds a threshold — feasible via ERC-7579 hooks or a Safe Guard's `checkAfterExecution`, but requires custom integration per target protocol, not a generic module.

### Gaps
- Could not confirm from the docs fetched whether any shipped module (Alchemy, Biconomy, ZeroDev) supports a native "USD value" denominated limit via an integrated oracle — this needs direct inspection of module source code or more specific documentation pages (e.g., Alchemy's "Wallet APIs session keys" reference page, not fully fetched here).
- Did not verify whether ZeroDev's Rate Limit Policy / Usage Limit Policy (per erc7579.com's description of "Smart Sessions") is actually deployed and audited in production versus documented as available — the erc7579.com page was treated as a module registry/ecosystem reference (likely Rhinestone-authored), and production/audit status of each specific policy module was not independently confirmed.
- Exact Safe{Core} AA module (the "Safe4337Module" enabling Safe accounts to act as ERC-4337 accounts) documentation details — including whether it exposes ERC-7579-style hooks or is validator-only — were not successfully fetched (the Safe docs fetch for smart-account-modules did not surface Safe4337Module specifics); this is a gap for the "how does Safe's own ERC-4337 path relate to 7579 modules" question.

## How do session keys (scoped, time-limited signing keys with permission constraints) relate to this problem, and can a session key be scoped so constraints are enforced on-chain rather than just advisory?

### Takeaway
Session keys are a *signing-authority* mechanism (who may produce a valid signature/authorization for a UserOp) that are composed with on-chain validator and policy/hook contracts; the actual constraint enforcement (value caps, target allowlists, time windows, rate limits) happens in those on-chain validator/policy contracts during the normal ERC-4337 validation+execution flow, not merely as off-chain/advisory metadata — meaning a correctly implemented session key's constraints are enforced by the EntryPoint/account contract and will cause the UserOperation to revert on-chain if violated, not just a client-side UX guard.

### Cited Findings
- Session keys "let you grant temporary, scoped permissions to a key without giving it full control of the account," defining what a key can do (specific contract calls, token transfers up to a limit) and for how long; session key modules allow a smart account to authorize a temporary signing key that can send transactions "only within a specified time window, only to specific contract addresses, and only up to a maximum value" — [Eco: ERC-7579 modular accounts](https://eco.com/support/en/articles/11890018-erc-7579-the-complete-guide-to-modular-smart-accounts)
- ZeroDev describes session keys as "keys assigned with specific permissions" — e.g. "a key that can only interact with Uniswap," "a key that can only use up to 1000 USDC," or "a key that expires in 3 days" — with permissions composable together; Kernel v4's permission system is "a composition of one signer and one or more policies," where validators validate UserOps/signatures and policies enforce rules like spending limits and target allowlists — [ZeroDev docs](https://docs.zerodev.app/smart-accounts/permissions/session-keys); [ZeroDev docs: Sudo Policy](https://docs.zerodev.app/sdk/permissions/policies/sudo)
- The Biconomy Session Key Manager Validation Module "verifies whether a given user operation adheres to the permissions defined within the session key and confirms that the operation has been signed by that session key" — i.e., the module itself (an on-chain validator contract called during `validateUserOp`) performs the constraint check, not an off-chain service — [Biconomy docs: Execute Transactions on Users' Behalf](https://docs.biconomy.io/new/smart-sessions/execute-transactions-on-users-behalf)
- Session keys compose with hooks for additional safety: a common pattern installs a session-key validator (authorizes which dApp/key may submit UserOps) alongside a separate spending-limit hook that enforces a hard daily cap independently — providing defense-in-depth where spending limits work even if the session-key validator logic has a flaw — [Eco: ERC-7579 modular accounts](https://eco.com/support/en/articles/11890018-erc-7579-the-complete-guide-to-modular-smart-accounts)

### Inferences
- "Scoped to trade only on protocol X, with constraints Y, enforced on-chain" is directly achievable today with shipped tooling: the session key's validator enforces *who* can sign and often *which target contract* is callable (protocol X), while a value-limit/usage-limit policy or hook enforces the *quantitative* constraints (Y). Both checks execute as part of the normal `validateUserOp`/execution path inside the EntryPoint's call into the smart account — they are not merely client-side SDK checks, so a violating UserOperation reverts on-chain before/during execution.
- The key architectural nuance for trading risk is that cross-operation state (e.g., cumulative daily loss, position-count-so-far) must be tracked in persistent contract storage read/written by the policy/hook contract itself (not just the session key's own static parameters), since a session key's permission grant is typically static (set at creation) while loss/position accumulate dynamically across many trades — this requires a stateful policy module, which the "Usage Limit Policy" / "interval-based spend limit" (Alchemy) patterns already demonstrate is implemented in production.

### Gaps
- Could not verify in this pass whether any of these session-key/policy systems have been independently security-audited specifically for the "cumulative loss" or "leverage" style stateful constraint (most documented examples are value-transfer caps per key or per interval, not P&L-aware). This is a meaningful gap: a max-daily-loss rule requires the on-chain hook to know realized/unrealized P&L, which typically requires reading external price feeds or protocol state — none of the docs fetched show a shipped "P&L-aware" policy module.

## What does EIP-7702 change, and does it let an existing EOA gain smart-account-like programmable constraints while keeping the same address?

### Takeaway
EIP-7702 (live on Ethereum mainnet since the Pectra upgrade, May 7, 2025) introduces transaction type `0x04` letting an EOA sign an authorization that installs a "delegation indicator" pointing at a contract's code into the EOA's own account — making calls to that EOA execute the delegate contract's logic while keeping the EOA's original address, balance, and nonce — which directly solves the "migrate to a new address" problem and allows a smart-account-style delegate (including ERC-7579 hooks/validators or Safe-like guards) to be installed on an existing, already-funded, already-identified EOA.

### Cited Findings
- EIP-7702 "introduces a new transaction type (0x04) that enables EOAs to delegate their execution to smart contracts while maintaining their original address and identity" via a signed "delegation designator," producing a "smart EOA": same address, same private key, but with batched transactions, gas sponsorship, session keys, and granular permissions — [HackerNoon: Turn a Regular Wallet into a Smart Account with EIP 7702](https://hackernoon.com/turn-a-regular-wallet-into-a-smart-account-with-eip-7702)
- EIP-7702 went live on Ethereum mainnet on May 7, 2025 as part of the Pectra hardfork; Arbitrum has also activated EIP-7702, letting EOAs there opt into the same delegation mechanism — [QuillAudits: EIP-7702 A New Era in Account Abstraction](https://www.quillaudits.com/blog/account-abstraction/eip7702-new-era-in-account-abstraction); [Arbitrum Foundation blog](https://blog.arbitrum.foundation/the-smartest-wallet-you-already-own-is-on-arbitrum/)
- Per the EIP-7702 spec itself: the transaction includes an "authorization list" of tuples `[chain_id, address, nonce, y_parity, r, s]`; for each valid tuple the protocol recovers the signer, validates the nonce, and writes a delegation indicator (`0xef0100 || address`) into the EOA's code field, after which `CALL`/`CALLCODE`/`DELEGATECALL`/`STATICCALL` targeting that EOA follow the pointer to execute the delegate's code within the EOA's own context/storage — [EIP-7702 spec](https://eips.ethereum.org/EIPS/eip-7702)
- Delegation is **persistent**, not per-transaction: the current design deliberately differs from earlier drafts that cleared code after each transaction, specifically to "create enough friction in deployment that users will not deploy new, unique [delegate contracts] regularly" — i.e., the EOA keeps behaving as the delegate's logic dictates across all future transactions until the delegation is explicitly changed or cleared — [EIP-7702 spec](https://eips.ethereum.org/EIPS/eip-7702)
- Security considerations flagged directly in the spec: delegate contracts must validate replay protection, transaction value, gas limits, target contracts, and calldata in their own signature-checking logic, since "a poorly implemented delegate can allow a malicious actor to take near complete control"; storage-layout collisions when switching delegates should be avoided using standards like ERC-7201; and clients should not accept multiple pending transactions for an EOA with a non-zero delegation indicator because delegated code can modify state unpredictably — [EIP-7702 spec](https://eips.ethereum.org/EIPS/eip-7702)
- Gas overhead comparison: EIP-7702 adds roughly ~42k gas for a basic UserOperation versus ~21k for a vanilla EOA transaction (delegation set once via the `SET_CODE` mechanism, with subsequent calls executing the implementation directly with minimal extra overhead), versus plain ERC-4337 smart accounts adding ~60k-120k extra gas (validation, paymaster check, bundler economics), with Safe 1-of-1 transactions adding roughly 50k-80k gas overhead above an equivalent EOA call — [BuildBear: ERC-4337 vs EIP-7702 Comparison](https://www.buildbear.io/blog/eip-4337-7702-comparison); [Ambire: Is ERC-4337 Really Bloated?](https://blog.ambire.com/erc-4337-gas-overhead-analysis/)
- Architecturally, ERC-4337 required no consensus/hard-fork change (shipped at the contract+bundler level, deployable on any EVM chain immediately), whereas EIP-7702 required a hard fork with client-level coordination (Pectra) — meaning EIP-7702 availability is chain-dependent on that chain having adopted the relevant hard fork, while ERC-4337 has been usable on essentially any EVM chain since its 2023 deployment — [BuildBear: ERC-4337 vs EIP-7702 Comparison](https://www.buildbear.io/blog/eip-4337-7702-comparison)
- Recommendation pattern emerging in the ecosystem: ERC-4337 (counterfactual smart contract accounts) is preferred for brand-new users/addresses, while EIP-7702 is preferred for **existing EOAs** where address reputation/continuity matters (ENS, social graph, on-chain history/credit) — directly relevant to a trader who doesn't want to migrate an established trading address — [BuildBear: ERC-4337 vs EIP-7702 Comparison](https://www.buildbear.io/blog/eip-4337-7702-comparison)
- ZeroDev ships "7702 Examples," indicating existing ERC-4337/ERC-7579 smart-account tooling (Kernel and its session-key/policy modules) is already being adapted to work via EIP-7702 delegation on existing EOAs rather than only on counterfactual smart-contract addresses — [ZeroDev: 7702 Examples](https://7702.zerodev.app/)

### Inferences
- EIP-7702 directly resolves the "migrate to a new address" objection for a trader with an existing, funded, reputationally-established EOA: they can delegate to a Kernel/Nexus/Modular-Account-style implementation (or a purpose-built risk-enforcement delegate) and gain the same ERC-7579 hook/policy/session-key machinery described above, without creating a new contract address or moving funds.
- Because delegation is persistent and the delegate contract's logic fully controls subsequent behavior of the EOA, the "poorly implemented delegate = near complete control" warning in the spec is a first-order risk for a trading-risk product: the delegate contract implementing the risk rules must itself be extremely well-audited, since it is not a bolt-on module sitting beside an immutable core (as with a well-audited Safe or Kernel implementation) but effectively *becomes* the account's entire logic.
- Given that ZeroDev already publishes 7702-specific examples, it's reasonable to infer (though not confirmed from primary audit evidence) that the ERC-7579 module ecosystem (Smart Sessions, spending-limit/rate-limit/usage-limit policies) is intended to be reusable as the EIP-7702 delegate target — i.e., the module/policy layer described in the platform comparison section above is not exclusive to "new smart contract wallet" deployments and is being positioned as the same layer an EIP-7702-upgraded EOA would use.

### Gaps
- Did not find a primary/official EIP-7702 adoption metric (e.g., % of EOAs delegated, transaction-type-4 volume on mainnet) for 2025-2026 — the search results describe the mechanism and gas comparisons but not usage/adoption statistics. This should be flagged as "mechanism confirmed live and documented; real-world adoption scale not quantified in sources reviewed."
- Did not confirm whether BSC (Binance Smart Chain), specifically named as in-scope by the task, has activated an equivalent of the Pectra/EIP-7702 hard fork — all EIP-7702 activation evidence found was for Ethereum mainnet and Arbitrum; BSC's EIP-7702 status is an open gap requiring direct confirmation (e.g., BNB Chain's own hard-fork changelog).

## How does the ERC-4337/account-abstraction approach compare to Safe+Guard specifically for trading risk limits — maturity, gas efficiency, composability with third-party DeFi protocols?

### Takeaway
Safe+Guard is the more battle-tested, simplest mechanism for blocking a non-compliant transaction outright (a Guard can revert pre- or post-execution on any `execTransaction`, including module-initiated ones as of Safe v1.5.0's module guards) and is protocol-agnostic since it wraps arbitrary calldata to any target contract; ERC-4337/ERC-7579 modular accounts (Safe's own AA module, Biconomy Nexus, ZeroDev Kernel, Alchemy Modular Account) add a standardized, portable module ecosystem purpose-built for session keys and spending-limit policies with richer constraint primitives (time windows, per-interval refreshing caps, usage/rate limits) but carry materially higher gas overhead (~60k-120k extra per op) than either a plain Safe multisig call (~50k-80k overhead) or an EIP-7702-delegated EOA (~42k overhead); for third-party DeFi composability, all three approaches are equally capable of calling arbitrary external contracts (the risk logic wraps the call, it doesn't limit which protocols can be targeted), so the choice is really about constraint-expressiveness and integration maturity rather than DeFi-protocol compatibility per se.

### Cited Findings
- A Safe Guard (`checkTransaction`/`checkAfterExecution`) blocks any Safe `execTransaction` by reverting, and as of Safe v1.5.0, **module guards** close the prior gap where module-initiated calls (e.g., from the Allowance Module or a custom automation module) could bypass the regular Guard's rules — giving Safe owners one consistent on-chain rule layer across both direct and module-initiated transactions — [Safe Foundation: Introducing Safe v1.5.0](https://safefoundation.org/blog/introducing-safe-v1-5-0-module-guards-enhanced-smart-account-features); [Safe docs: Guard tutorial](https://docs.safe.global/advanced/smart-account-guards/smart-account-guard-tutorial)
- Gas overhead ordering found: EIP-7702 (~42k extra gas for a basic UserOp) < Safe 1-of-1 (~50k-80k overhead over an equivalent EOA call; ~115k-145k total for a USDC transfer vs ~65k from an EOA) < plain ERC-4337 smart accounts (~60k-120k extra gas for validation, paymaster check, bundler economics; ~150k-250k total for simple calls) — [BuildBear: ERC-4337 vs EIP-7702 Comparison](https://www.buildbear.io/blog/eip-4337-7702-comparison); [Ambire: Is ERC-4337 Really Bloated?](https://blog.ambire.com/erc-4337-gas-overhead-analysis/)
- Safe itself now ships its **own ERC-4337 module** (referred to in the research task as "Safe{Core} AA"), meaning Safe is not mutually exclusive with ERC-4337 — a Safe account can operate both via classic `execTransaction`+Guards and via ERC-4337 UserOps through its AA module, letting a team reuse Safe's mature Guard/module audit history while optionally gaining ERC-4337's bundler/paymaster UX — [Eco: Safe Wallet Deep Dive 2026](https://eco.com/support/en/articles/15254042-safe-wallet-deep-dive-2026-multisig-and-smart-accounts) (Note: specific Safe4337Module technical documentation could not be fetched in this research pass — see Gaps.)
- ERC-7579's portability claim — "modules written for Nexus are portable to other 7579-compliant accounts" — means a spending-limit/session-key policy module built against the ERC-7579 standard is reusable across Biconomy, and (per ecosystem docs) other 7579 accounts, which Safe's own bespoke Guard interface does not offer (a Safe Guard is Safe-specific, not a cross-vendor standard) — [Eco: Best Smart Wallet SDKs for Developers (2026)](https://eco.com/support/en/articles/14797815-best-smart-wallet-sdks-for-developers-2026)
- The ERC-7579/Smart Sessions module ecosystem offers materially richer named constraint primitives out of the box (Spending Limits, Time Frame, Usage Limit/Rate Limit, Value Limit, Universal Action/target-allowlist, Sudo-override policies) than the Safe Allowance Module's single documented primitive (amount spendable per period) — [ERC-7579 Modules](https://erc7579.com/modules); [Remix (X/Twitter) on Safe Modules/Guards](https://x.com/EthereumRemix/status/2024424369032716551)
- ERC-4337 "required no consensus changes... shipped fast, deployed everywhere EVM ran" vs. EIP-7702 requiring a hard fork — meaning ERC-4337 (and Safe, which predates and doesn't depend on either) have longer production track records and wider chain support today than EIP-7702, which is only live on chains that adopted the relevant hard fork (confirmed for Ethereum mainnet and Arbitrum; BSC status unconfirmed, see prior section's Gaps) — [BuildBear: ERC-4337 vs EIP-7702 Comparison](https://www.buildbear.io/blog/eip-4337-7702-comparison)

### Inferences
- For a trading-risk-limits product specifically, the "best" approach is not strictly either/or: a Safe Guard is the simplest, most audited way to get a hard revert-based backstop (e.g., an absolute transaction cap or recipient allowlist) with minimal new infrastructure, while an ERC-7579 modular account (via Safe's own AA module, Biconomy Nexus, or ZeroDev Kernel) is better suited when the product needs composable, swappable, cross-vendor-portable policies with richer semantics (rolling time-window caps, usage counts, per-session scoping) — the two are complementary rather than strictly competing, especially since Safe itself bridges both by shipping an ERC-4337 module.
- Given gas costs, EIP-7702 delegation to a purpose-built risk-enforcement delegate (potentially itself using ERC-7579-style hooks internally) is the most gas-efficient path for an *existing* EOA that wants programmable constraints, but it inherits the highest architectural risk (a flawed delegate grants "near complete control," per the EIP's own security considerations) and the narrowest chain support of the three options as of this research (not yet confirmed on BSC).
- "Composability with arbitrary third-party DeFi protocols" is not meaningfully differentiated between Safe+Guard, ERC-4337 modular accounts, or EIP-7702 delegates — all three ultimately execute arbitrary calldata to arbitrary target contracts, and the risk constraints are enforced by wrapping/intercepting that call (Guard, hook, or delegate logic) rather than by limiting which protocols can be called; the real differentiator is how expressive and standardized the wrapping constraint layer is, not whether the account *can* reach a given DeFi protocol.
