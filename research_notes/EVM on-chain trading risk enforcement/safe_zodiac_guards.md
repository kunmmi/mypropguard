# Safe (Gnosis Safe) + Zodiac Guards for On-Chain Trading Risk Enforcement

## How do checkTransaction and checkAfterExecution work mechanically, and can they revert the transaction?

### Takeaway
A Safe Guard is a contract hook, set via `setGuard(address)`, that the Safe's `execTransaction` calls synchronously immediately before (`checkTransaction`) and immediately after (`checkAfterExecution`) running the underlying transaction; a revert in either call reverts/blocks the whole Safe transaction, giving Guards real veto power — but only over transactions that go through `execTransaction` (owner-signed multisig flow), not over Module transactions (which use a separate, optional `moduleGuard`/`checkModuleTransaction` hook introduced later).

### Cited Findings
- Guards were introduced in Safe (Gnosis Safe) smart contracts v1.3.0 and are smart contracts that add restrictions on top of the Safe's n-out-of-m signature scheme, with checks run before and after execution of a Safe transaction — [Safe Guards docs](https://docs.safe.global/advanced/smart-account-guards)
- The `checkTransaction` function signature (per Safe's own tutorial) is: `function checkTransaction(address to, uint256 value, bytes memory data, Enum.Operation operation, uint256 safeTxGas, uint256 baseGas, uint256 gasPrice, address gasToken, address payable refundReceiver, bytes memory signatures, address msgSender) external` — [Building a Guard for Safe Smart Account](https://docs.safe.global/advanced/smart-account-guards/smart-account-guard-tutorial)
- The post-execution hook signature is `function checkAfterExecution(bytes32 txHash, bool success) external` — [Building a Guard for Safe Smart Account](https://docs.safe.global/advanced/smart-account-guards/smart-account-guard-tutorial)
- `checkTransaction` receives raw/unparsed transaction fields — the destination address, raw `data` bytes, an `Enum.Operation` (0=Call, 1=DelegateCall), and the gas/refund/signature parameters — not any pre-decoded semantic representation of the call — [Building a Guard for Safe Smart Account](https://docs.safe.global/advanced/smart-account-guards/smart-account-guard-tutorial)
- "A revert in checkTransaction prevents transaction execution" and a Guard "has full power to block Safe transaction execution" — [Safe Guards docs](https://docs.safe.global/advanced/smart-account-guards); corroborated: "Guards are hooks that run pre/post-execution for validation checks (like a firewall)... only the Safe itself (through multisig) can change it" — [search synthesis of docs.safe.global](https://docs.safe.global/advanced/smart-account-guards)
- To attach a Guard, the Safe calls its own `setGuard(address guard)` function (passing `address(0)` disables it); this requires a normal Safe transaction (i.e., owner multisig approval) but does **not** require redeploying or changing the Safe's address — [setGuard reference](https://docs.safe.global/reference-smart-account/guards/setGuard)
- Guards are explicitly flagged by Safe as security-critical: "a broken guard can cause a denial of service for the Safe" since it can block all fund access; Safe recommends careful audits and designed recovery mechanisms (e.g., ability to remove/replace the guard) — [Safe Guards docs](https://docs.safe.global/advanced/smart-account-guards)
- A separate `setModuleGuard` exists for adding equivalent pre/post hooks (`checkModuleTransaction`) specifically to transactions executed via Safe Modules (as opposed to direct owner-signed `execTransaction` calls) — [setModuleGuard reference](https://docs.safe.global/reference-smart-account/guards/setModuleGuard)
- Community/security commentary (Ackee Blockchain) on Safe transaction flow and Guard usage as a defensive layer post-Bybit-hack discusses the Guard as the Safe-native mechanism for blocking malicious/unexpected transactions before signature execution completes — [A Safe-native Solution to the Bybit Hack](https://ackee.xyz/blog/a-safe-native-solution-to-the-bybit-hack/)

### Inferences
- Because `checkTransaction` fires inside the same call frame as `execTransaction` and can revert, a Guard behaves like an atomic, synchronous on-chain policy gate: there's no "advisory" mode — the Guard's logic is one of the strictest parts of the transaction path and any revert reason or gas-expensive logic directly affects every transaction the Safe ever sends.
- `checkAfterExecution` is state-based, not calldata-based: because it runs after state changes, it's the natural place to enforce output-dependent rules (e.g., "the Safe's token balance must not have dropped by more than X%"), whereas `checkTransaction` is the natural place for input-dependent rules (e.g., "target must be an allow-listed exchange contract").
- A Guard enforces rules only on the subset of execution paths it's wired into. A full risk-enforcement design needs both a transaction Guard (for owner-initiated calls) and a module Guard (for module-initiated calls, e.g. automated bots using a Zodiac module) to have no bypass path.

### Gaps
- Safe's own docs page content (beyond the tutorial) did not surface exact wording on whether `checkAfterExecution` can itself still revert a transaction already marked `success=true` on-chain (practically, since it runs inside the same transaction, a revert there would revert the whole transaction including the already-executed inner call, but this was not explicitly confirmed with an exact doc quote).

## Can a Guard decode semantic meaning of transactions, or only raw calldata — and what are the practical limits of generic decoding vs. per-protocol logic?

### Takeaway
A Guard only ever receives the raw `to` address, raw `value`, and raw `data` bytes (undecoded) — there is no generic or automatic semantic layer; any "this is a $50k Uniswap swap" or "this opens 10x leverage on GMX" recognition must be hand-written per-protocol ABI-decoding logic inside the Guard contract itself, and this does not generalize to arbitrary/unknown third-party contracts.

### Cited Findings
- `checkTransaction`'s `data` parameter is passed as raw `bytes memory`; Safe's own tutorial demonstrates only a trivial check (e.g., on `operation` type), not calldata decoding, and provides no protocol-decoding guidance — [Building a Guard for Safe Smart Account](https://docs.safe.global/advanced/smart-account-guards/smart-account-guard-tutorial)
- Safe's separate decoder service (`safe-decoder-service`, used by the Safe{Wallet} UI to show human-readable transaction previews to signers) is a distinct off-chain/indexer component from the on-chain Guard, and even that service has had to impose hard limits — a `DECODER_MAX_NESTED_DEPTH` (default 8) — because nested MultiSend/execTransaction calldata decoded recursively without limit caused memory usage to grow quadratically with payload size — [safe-decoder-service PR #355](https://github.com/safe-global/safe-decoder-service/pull/355)
- The same decoder-service hardening work highlights a semantic trap in generic decoding: a delegatecall-shaped payload sent to a non-MultiSend contract could "report approvals that never execute," i.e., naive calldata decoding can misrepresent what a transaction actually does if the call is a delegatecall into unexpected code — [safe-decoder-service PR #355](https://github.com/safe-global/safe-decoder-service/pull/355)
- Zodiac's **Roles Modifier** module takes the opposite, purpose-built approach to parameter-level semantic scoping: it lets a role "scope calls down to specific parameter conditions" (e.g. "may call `approve`, but only for this one spender," or "may call `swap`, but only if `min_amount_out` clears some floor") using an explicit, per-function "condition" expression configured by the account owner — this requires the function selector and ABI layout to be known and configured in advance per target contract/function — [Zodiac Roles Modifier docs](https://docs.roles.gnosisguild.org/) and [gnosisguild/zodiac-modifier-roles](https://github.com/gnosisguild/zodiac-modifier-roles)
- Roles Modifier's "allowances" feature implements threshold/rate-limit tracking (e.g., a running budget that decrements per call and reverts once exhausted), again implemented as specific, pre-configured scoping rules rather than generic semantic transaction understanding — [Zodiac Roles Modifier API reference](https://docs.roles.gnosisguild.org/sdk/api)
- Roles Modifier ships a dedicated, protocol-specific integration for CowSwap (`allowCowOrderSigning`), configured with explicit sellable/buyable token allow-lists — illustrating that even the most semantically capable Zodiac component still needs bespoke, protocol-aware configuration per DEX/venue rather than deriving trade semantics automatically — [Zodiac Roles Modifier API reference](https://docs.roles.gnosisguild.org/sdk/api)

### Inferences
- There is no generic, protocol-agnostic way for an on-chain Guard (or Zodiac Roles condition) to infer "semantic meaning" like position size or leverage from arbitrary calldata to an arbitrary third-party contract. Every example found requires the integrator to already know the target contract's ABI/selector and write matching decode/condition logic for it.
- This means a Guard enforcing "max position size" or "max leverage" against, say, GMX or a perps DEX, has to be written specifically against that protocol's order/position-opening function signature(s) — recognizing the function selector, decoding the relevant parameters (notional size, leverage multiplier, collateral token) and comparing against on-chain state or an oracle. A new integrated protocol or even a new version of an existing protocol's contract can silently break or bypass the Guard's checks if the Guard wasn't updated to match the new calldata shape.
- Guards can only reliably control "which contracts/functions may be called, with which decoded parameters" (an allow-list + per-function condition model, as Zodiac Roles already implements) — they cannot generically "understand" an arbitrary call the way a human reading a block explorer transaction simulation would.
- Practical limit: for DEX aggregators or routers where the actual swap path/target is itself embedded deep inside opaque calldata (e.g., 1inch/0x style multi-hop routes), semantic decoding of "what is really being traded against what" inside a Guard becomes very hard to do safely and cheaply on-chain; this pushes real deployments toward allow-listing specific, audited router/protocol entry points rather than trying to decode arbitrary aggregator calldata.

### Gaps
- No concrete example was found of a Guard (or Roles condition) specifically decoding GMX or another perps-protocol's leverage-opening calldata to enforce a max-leverage rule; this appears to be a gap in publicly documented/audited implementations, not something ruled out mechanically — flagging as unconfirmed in practice rather than confirmed-impossible.
- Could not confirm a documented maximum calldata size or standardized fallback behavior that Guards themselves must adopt when they encounter calldata shapes they don't recognize (e.g., revert-by-default vs. allow-by-default) — this is a design decision left to each Guard's author per the sources found.

## Does using a Guard require migrating to a new Safe address, and can an existing EOA become Safe-controlled without changing its address (CREATE2 / EIP-7702)?

### Takeaway
Attaching a Guard does **not** require a new Safe address — `setGuard` is called on the trader's existing, already-deployed Safe via a normal Safe transaction. However, converting a pre-existing plain EOA (not a Safe) into a Guard-protected account without changing its address was, until EIP-7702, essentially impossible on general EVM chains; EIP-7702 (live since the Pectra upgrade, May 7, 2025) now lets an EOA attach smart-contract logic to itself at its existing address, and Safe has proposed registering Safe itself as a valid EIP-7702 delegation target.

### Cited Findings
- A Guard is attached to an existing Safe by calling that Safe's own `setGuard(address guard)` function; this is a standard Safe transaction (subject to the existing owner-threshold signing policy) and does not involve redeploying the Safe or changing its address — [setGuard reference](https://docs.safe.global/reference-smart-account/guards/setGuard)
- CREATE2 cannot be used to "take over" an address that already has nonzero nonce or non-empty code — i.e., CREATE2 cannot turn an already-used EOA address into a Safe's address; CREATE2's counterfactual-deployment trick only works for addresses that have never been used/deployed to — [CREATE2 deterministic deployment discussion](https://medium.com/@ivanlieskov/demystifying-create2-and-permit2-deterministic-smart-contract-deployment-in-ethereum-c15548c7a198)
- An EOA's address is derived deterministically from its public key and is the same across EVM chains; without EIP-7702, there was no way to move an EOA's existing funds/address into smart-contract (Safe-style) control without actually transferring assets to a different address — [EOA vs Smart Wallet](https://eco.com/support/en/articles/14796239-eoa-vs-smart-wallet-key-differences)
- EIP-7702 was activated May 7, 2025 as part of Ethereum's Pectra upgrade, and lets an EOA "temporarily delegate execution to a smart contract by attaching code to its address for the duration of a transaction" — the EOA's address itself never changes — [ERC-7702 Deep Dive 2026](https://eco.com/support/en/articles/15254037-erc-7702-deep-dive-2026-eoa-becomes-smart-wallet); corroborated by [What Is EIP-7702?](https://eco.com/support/en/articles/10442528-what-is-eip-7702-smart-eoa-wallets-for-pectra)
- "Safe has proposed a path for existing Safe deployments to register as valid delegation targets for EIP-7702, which would allow individual EOA signers on a Safe to grant temporary elevated permissions without creating a new address" — [search synthesis citing Safe's public EIP-7702 commentary](https://x.com/safe/status/1848688222554968234)
- Base's engineering blog describes a specific "proxy pattern for Safe EOA-to-smart-wallet transitions" under EIP-7702, addressing security considerations for EOAs delegating to Safe-style logic while retaining their original address — [Securing EIP-7702 Upgrades: A Proxy Pattern for Safe EOA-to-Smart Wallet Transitions](https://blog.base.dev/securing-eip-7702-upgrades)

### Inferences
- For a trader who is already using a Safe, adding Guard-based risk enforcement is a zero-migration operation — no loss of trading history/reputation tied to that Safe's address, since the address never changes.
- For a trader currently operating from a plain EOA (the much more common case for individual/bot traders on DEXs), there are two realistic non-custodial-address-preserving paths as of late 2025/2026: (1) EIP-7702 delegation, where the EOA designates Safe (or another smart-account implementation) as its code and so gains Guard-style programmability while keeping its address and on-chain history/reputation intact; or (2) accepting a new Safe address (losing continuity) by counterfactually deploying a Safe up front for new traders. CREATE2 does not help migrate an *existing*, already-active EOA to Safe-like semantics at the same address — it only helps predict/pre-fund a *future* Safe address before first use.
- EIP-7702 delegation is described in sources as attaching code "for the duration of a transaction" in some framings and more persistently in others (varying by wallet/tooling implementation) — this nuance (session-scoped vs. persistent delegation) matters a lot for whether Guard-style checks apply to literally every future transaction from that EOA or only to transactions explicitly routed through the delegation; this distinction was not fully resolved by the sources gathered.

### Gaps
- Could not find a confirmed, audited, production example (mainnet or BSC) of an EOA using EIP-7702 to delegate specifically to a Safe + Guard combination for the purpose of trading risk enforcement, as opposed to general smart-account conveniences (batching, gas sponsorship, session keys). This remains a 2025/2026 forward-looking capability more than a proven deployed pattern per the sources found.
- Did not confirm whether EIP-7702 delegation persists across all future transactions by default or must be re-authorized/re-signed periodically — material to whether a Guard attached via 7702-Safe delegation provides durable, always-on enforcement or only per-session enforcement. Flagging as an open question requiring direct review of EIP-7702's specification and current wallet implementations (MetaMask, etc.) rather than the secondary sources used here.

## Real-world examples of Guards for trading-risk limits (vs. DAO treasury spending limits)

### Takeaway
Documented, named Guard/module examples found in Zodiac's own ecosystem and Safe's reference material are overwhelmingly DAO-treasury-oriented (spend scoping, delegatecall restriction, exit/rage-quit, oracle-triggered execution) rather than trading-risk-specific (position size, leverage, daily loss); the one risk-limit example surfacing in search results (OpenAlice) describes pre-trade "guard" middleware conceptually similar to a Safe Guard but was not confirmed to actually be built on Safe/Zodiac's `checkTransaction` interface.

### Cited Findings
- Zodiac's own architecture documentation describes Guards generically as enabling things like "limit[ing] the scope of addresses and functions that a module can call" or "ensur[ing] a certain state is never changed by a module" — framed around module/DAO governance safety, not trading-specific risk metrics — [Zodiac README](https://github.com/gnosisguild/zodiac/blob/master/README.md)
- Named Zodiac modules found in the GitHub organization are treasury/governance-oriented: the Reality Module (uses Reality.eth as an oracle to trigger Safe execution), the Exit Module (lets token holders redeem/rage-quit a share of a DAO treasury), and the Siphon Module — none are framed as trading-position risk controls — [gnosisguild/zodiac-module-reality](https://github.com/gnosisguild/zodiac-module-reality), [gnosisguild/zodiac-module-exit](https://github.com/gnosisguild/zodiac-module-exit), [gnosisguild/zodiac-module-siphon](https://github.com/gnosisguild/zodiac-module-siphon)
- A concrete, publicly listed Safe Guard example closer to "restricted actions" than pure DAO spend limits: `RestrictedActionsGuard`, described as "a Safe Guard that allows owners to only perform allowed actions to whitelisted contracts with a different threshold" — a generic allow-list/threshold pattern that could underpin (but is not itself) a trading risk limit — [aviggiano/safe-restricted-actions-guard](https://github.com/aviggiano/safe-restricted-actions-guard)
- Another named, older Guard referenced via Safe's own Guards documentation is Gnosis's `ScopeGuard`, which restricts which function selectors/targets a Safe may call — again a generic access-control primitive rather than a trading-risk-specific guard — [gnosis/ScopeGuard](https://github.com/gnosis/ScopeGuard)
- OpenAlice's documentation describes "guards" as "optional push-time middleware that run inside each UTA before orders reach the broker," including a "max-position-size" guard that "estimates the projected position value after the order and compares it to net liquidation" and rejects orders exceeding a configured `maxPercentOfEquity` threshold — this is conceptually exactly the kind of pre-trade risk Guard the research objective is asking about, but the source found does not establish whether OpenAlice's implementation is actually built on the Safe/Zodiac `checkTransaction` Guard interface specifically (vs. its own off-chain or different on-chain middleware) — [OpenAlice: Guards & Risk](https://www.openalice.ai/docs/trading/guards-and-risk)
- Zodiac's Roles Modifier is explicitly marketed with trading-adjacent features (per-function parameter scoping, allowances/rate limits, and a CowSwap-specific integration for permissioned order signing), which is the closest found example of Zodiac tooling purpose-built to touch on trading flows, though it is framed as a permissions/allowance system rather than a specific "max leverage" or "max daily loss" circuit breaker — [Zodiac Roles Modifier docs](https://docs.roles.gnosisguild.org/)
- No results were found for a Zodiac or Safe module/Guard literally named or documented as a "circuit breaker" for trading risk — [search: Zodiac github.com/gnosis/zodiac module library circuit breaker]
- Broader market context: the dominant real-world pattern for "daily loss limits" / "max drawdown" in the prop-trading industry runs on centralized trading-server enforcement (e.g., proprietary trading firm platforms, MetaTrader-based tooling), not on-chain Safe/Zodiac Guards — search results on prop-firm daily-loss enforcement returned centralized/off-chain examples only, with no on-chain Safe-based implementation surfacing — [search: prop trading firm Safe Gnosis guard max daily loss enforce on-chain]

### Inferences
- The Safe/Zodiac ecosystem's existing, audited, named building blocks (ScopeGuard, RestrictedActionsGuard, Roles Modifier's allowances/conditions) are generic access-control and rate-limiting primitives that a team could compose into a bespoke trading-risk Guard (allow-list the DEX/perps router, scope the relevant open-position function, bound its notional/leverage parameter, track a rolling-window allowance for "daily loss"), but no fully pre-built, audited, drop-in "max position size / max leverage / max daily loss" Guard specifically for trading was found in the public Zodiac module library or Safe's reference docs as of this research.
- This is a legitimate build-vs-buy gap: a team building this kind of guard would very likely need to write and separately audit custom Guard/Roles-condition logic rather than deploy an existing community-audited module, increasing both the development and audit cost/timeline versus treasury-spend-limit use cases which have mature prior art.

### Gaps
- Could not confirm whether OpenAlice (or any other named product) is actually deployed on top of Safe's `IGuard`/`checkTransaction` interface versus a separate/custom on-chain or off-chain risk layer; this needs direct inspection of OpenAlice's contracts/source, which was outside the scope of the searches performed.
- No audit report specifically covering a "trading risk Guard" (position size/leverage/daily-loss) was found from Trail of Bits, OpenZeppelin, or similar firms; searches surfaced only generic smart-contract-audit market/pricing information and an unrelated price-oracle audit (Euler), not a Guard-specific audit. This appears to be a genuine gap in publicly available audit literature, not a search failure alone — worth a follow-up search restricted to audit-firm report archives/GitHub security-review repos if deeper confirmation is needed.

## Gas and composability costs/limits of Guards (e.g., calling external price oracles during checks)

### Takeaway
No source found during this research quantifies the actual gas cost of a Safe Guard call or of a Guard making an external oracle call during `checkTransaction`; what is documented is that Guards run unconditionally on every Safe transaction (so their gas cost is additive to every single transaction, forever, as long as the Guard is attached) and that overly complex/unbounded on-chain logic in a Guard (e.g., unbounded recursive decoding) has caused real resource-exhaustion problems in Safe's own tooling.

### Cited Findings
- `checkTransaction` and `checkAfterExecution` are external calls made by the Safe contract as a mandatory part of every `execTransaction`, meaning their gas cost is paid on top of the underlying transaction's cost on every single Safe transaction for as long as the Guard remains set — [Safe Guards docs](https://docs.safe.global/advanced/smart-account-guards)
- Safe's `safeTxGas` parameter (passed into `checkTransaction`) exists specifically to let the Safe transaction's gas allowance be set/estimated per transaction, implying Guard logic must be accounted for within normal Safe transaction gas estimation and budgeting flows rather than being "free" or off-chain — [Building a Guard for Safe Smart Account](https://docs.safe.global/advanced/smart-account-guards/smart-account-guard-tutorial) (parameter present in the `checkTransaction` signature)
- Unbounded/naive on-chain decoding logic is a documented real-world cost and risk: Safe's decoder-service team found that recursive decoding of nested MultiSend/execTransaction payloads with no depth limit caused memory usage to scale quadratically with payload size, requiring a hard-coded `DECODER_MAX_NESTED_DEPTH` (default 8) to contain it — while this was in an off-chain service rather than an on-chain Guard, it is directly analogous to the computational risk an on-chain Guard would face if it tried to generically decode arbitrary/nested calldata rather than targeted, bounded checks — [safe-decoder-service PR #355](https://github.com/safe-global/safe-decoder-service/pull/355)
- Zodiac Roles Modifier's "allowances" feature (threshold/rate-limit tracking referenced against stored on-chain state) is the closest documented example of a Guard-adjacent component doing more than trivial comparisons, implying state reads/writes (SLOAD/SSTORE) on every gated call, but no specific gas numbers were given in the source — [Zodiac Roles Modifier API reference](https://docs.roles.gnosisguild.org/sdk/api)

### Inferences
- Because a Guard call is synchronous and part of the same transaction, any external call it makes (e.g., to a Chainlink-style price oracle to value a position in USD for a "max position size" check) adds that oracle call's full gas cost (a `STATICCALL`/`CALL`, likely cold-SLOAD-heavy on first access per block) directly to the cost of every single trade the Safe executes — there is no way to make this "free" or amortized; it is paid every time, by whoever submits the transaction.
- A Guard that calls out to a price oracle also inherits all of that oracle's composability/trust risks (oracle staleness, manipulation, or unavailability) directly into the trade-execution path — if the oracle call reverts or returns stale/implausible data and the Guard does not handle that gracefully, every trade can be blocked (a DoS risk Safe's own docs already flag generically for "broken guards").
- The directly analogous data point (recursive decoding causing quadratic memory blow-up) is a strong, concrete warning that a Guard attempting broad, generic multi-protocol calldata decoding (rather than narrow, protocol-specific, bounded checks) risks both excessive gas costs and new attack surface (DoS via crafted deeply-nested or oversized calldata), reinforcing that practical Guard designs should keep decoding narrow and bounded rather than general-purpose.

### Gaps
- No concrete gas-unit figures (e.g., "~30k gas for a basic checkTransaction call" or "~80k extra gas to query a Chainlink price feed from within a Guard") were found in any source reviewed. This would need direct measurement (e.g., via Foundry/Hardhat gas reports on a reference Guard implementation) rather than being available in existing public documentation or blog posts found in this search.
- No source discussed cross-chain gas cost differences specifically for BSC vs. Ethereum mainnet Guard execution (e.g., BSC's lower gas price environment potentially making heavier Guard logic, like multi-oracle cross-checks, more economically viable there) — this is a gap specific to the BSC angle requested and was not covered by any source found.
