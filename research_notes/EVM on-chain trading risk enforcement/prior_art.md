# Prior Art: On-Chain-Enforced Trading/Spending Risk Limits (EVM, Front-End-Independent)

## Safe's Allowance Module / Spending Limit Module — mechanics, scope, and extensibility to trading limits

### Takeaway
Safe's Allowance Module is a genuinely preventive, front-end-independent enforcement mechanism (it is a Safe Module with direct `execTransactionFromModule` rights, so it works no matter what UI a delegate uses) — but it only validates a single scalar (cumulative ERC-20/ETH amount per token per time window) against hard-coded transfer calls. It has no concept of decoding arbitrary calldata, so it cannot be mechanically extended to position size or leverage without a substantially different, protocol-specific module.

### Cited Findings
- The Allowance Module is a Safe Module — a separate contract the Safe authorizes to call `execTransactionFromModule` and move funds without collecting threshold signatures; Modules are how Safe extends from a static multisig into a programmable account — [docs.safe.global](https://docs.safe.global/home/ai-agent-quickstarts/agent-with-spending-limit)
- Per Safe, you set an allowance per token for a spender/"delegate," either one-time or resetting on an interval (e.g., 100 USDC every day); configurable fields are beneficiary (any address, owner or not), asset (ETH or any ERC-20), amount, and reset time (one-time, daily, weekly, monthly) — [help.safe.global](https://help.safe.global/articles/3961440620-set-up-and-use-spending-limits), [docs.safe.global](https://docs.safe.global/home/ai-agent-quickstarts/agent-with-spending-limit)
- Contract-level mechanics (from the Allowance Module source on safe-global/safe-modules): state is a mapping keyed by (Safe, delegate, token) storing `amount` (uint96 cap), `spent` (cumulative usage), `resetTimeMin` (uint16 renewal interval in minutes, max ~45 days), `lastResetMin`, and `nonce` (uint16 replay protection, max 65,536 transfers); `delegates`/`tokens` index structures let anyone enumerate all allowances for a Safe so none are hidden — [github.com/safe-global/safe-modules](https://github.com/safe-global/safe-modules/tree/main/modules/allowances)
- Execution path: `executeAllowanceTransfer` verifies the delegate's EIP-712 signature, checks the requested amount against remaining allowance, and only then instructs the Safe to perform one of two hard-coded operations — a direct ETH transfer or an ERC-20 `transfer` call; it does not parse or validate arbitrary transaction calldata — [github.com/safe-global/safe-modules](https://github.com/safe-global/safe-modules/tree/main/modules/allowances)
- Because the module recognizes only these two transfer shapes, it structurally cannot validate "trade" parameters like position size, leverage, or notional exposure inside a DEX/perp call — extending the pattern to derivatives would require a different module that decodes target-contract calldata and checks domain-specific fields, not a parameterization of the existing one — [github.com/safe-global/safe-modules](https://github.com/safe-global/safe-modules/tree/main/modules/allowances) (synthesis from module mechanics above)

### Inferences
- The Allowance Module is the clearest existing example of "hard, unbypassable, front-end-independent" enforcement on EVM — the limit is checked inside the Safe's own module-call path, not by any cooperating signer or front-end — but its enforceable surface is narrow by design (simple value transfers only).
- A trading-limit analog (e.g., for perps) would need to be its own Zodiac/Safe-style Guard or Module that whitelists a specific target contract (e.g., a perp DEX router) and decodes its function arguments (size, leverage, direction) rather than reusing Allowance Module's transfer-amount logic — this is an architecture fork, not a parameter change.

### Gaps
- No primary source (Safe docs/repo) explicitly discusses or rules out extending Allowance Module to non-transfer call types; the "could it be extended" conclusion above is an inference from its documented data model, not a stated roadmap item.

## DeFi Saver and Instadapp automation — preventive Guard/module vs. reactive bot

### Takeaway
Both DeFi Saver's and Instadapp's position-automation (stop-loss, auto-repay/auto-boost, liquidation protection) are reactive, bot-triggered systems that execute an on-chain transaction after a monitored condition is crossed — not a Guard/module that blocks a bad transaction preemptively at signing time. The smart contracts provide non-custodial, trustless *execution* of a pre-authorized recipe; they do not continuously gate every account action the way a Safe Guard or Allowance Module does.

### Cited Findings
- DeFi Saver's "Strategy" consists of triggers plus a Recipe executed when conditions are met; the chain of contracts is `StrategyExecutor` → `ProxyAuth` (immutable, callable only by StrategyExecutor) → `RecipeExecutor.executeRecipeFromStrategy`, which then calls the user's DSProxy to run the recipe — [blog.defisaver.com](https://blog.defisaver.com/automated-strategies-technical-overview/)
- `RecipeExecutor` "checks if trigger conditions are met, and executes the recipe" — i.e., condition-check and execution happen together, off a bot-submitted transaction, not as a pre-trade gate baked into every transaction the account can send — [blog.defisaver.com](https://blog.defisaver.com/automated-strategies-technical-overview/)
- Some recipe parameters (e.g., boost amount depending on current CDP ratio, optimal exchange routing) are computed off-chain at execution time, meaning the bot/keeper layer plays an active role in deciding the specifics of the protective action, not just relaying a user-signed instruction — [blog.defisaver.com](https://blog.defisaver.com/automated-strategies-technical-overview/)
- This architecture contains an inherent latency gap: because triggers are monitored and reacted to (not enforced as an atomic precondition on every transaction), a position can in principle move adversely or even be liquidated in the window between trigger crossing and bot execution; no DeFi Saver source reviewed addresses or quantifies this latency risk — [blog.defisaver.com](https://blog.defisaver.com/automated-strategies-technical-overview/) (synthesis)
- Instadapp's DeFi Smart Accounts (DSA) are modular contract accounts with "Connectors" (protocol adapters) and an "Authority" framework; Protection Automation for Aave v3 watches a Health Factor and unwinds debt when a "Triggering Health Factor" is crossed, aiming for a "Target Health Factor" — this requires granting automation authority over the DSA, which is added when automation is activated and removed when canceled — [guides.instadapp.io](https://guides.instadapp.io/features/protection-automation), [guides.instadapp.io](https://guides.instadapp.io/dive-deeper/defi-smart-accounts)
- Instadapp previously partnered with Gelato Network ("Instadapp Actions") to provide automated debt refinancing between lending protocols specifically to preempt costly liquidations — an explicitly bot/keeper-network-driven design — [beincrypto.com](https://beincrypto.com/instadapp-actions-automates-defi-for-liquidation-protection/), [tokenpost.com](https://www.tokenpost.com/Instadapp-Actions-Automates-DeFi-For-Liquidation-Protection-6407)

### Inferences
- Both products are best classified as "fast-reactive," not "preventive" in the sense this research distinguishes: they do not block a user (or front-end) from entering an oversized or excessively leveraged position in the first place; they instead watch health/price metrics and submit a corrective transaction after a threshold is crossed, which is architecturally the same class of pattern as MyPropGuard-on-Hyperliquid's weaker "check-then-cosign" model, just automated and keeper-driven rather than human-driven.
- Neither uses a Safe-style Guard/Module hook that runs synchronously inside the user's own transaction to reject it before a limit is exceeded.

### Gaps
- No team interview or blog post from DeFi Saver or Instadapp was found that explicitly frames their own design as "reactive by necessity" versus a hypothetical preventive alternative, or that quantifies real-world latency/slippage incurred between trigger and execution (flagged as a documented gap in the fetched DeFi Saver technical post itself).

## Known "circuit breaker" smart contract wallets / trading risk products in the wild

### Takeaway
Outside of DAO treasury-Guard tooling (below), genuinely preventive, generalized "trading circuit breaker" wallets for EVM do not appear to exist as shipped products; what surfaces under these search terms is either (a) DAO/treasury spending-limit infrastructure, (b) token-level circuit breakers embedded in a single protocol's own contracts (not wallet-level, not generalized), or (c) marketing language from "on-chain prop firms" whose actual enforcement mechanism is not transparently documented.

### Cited Findings
- Generic descriptions of "programmable wallets" list spending rules "enforced in code before signing a transaction" — per-tx caps, session/daily budgets, recipient allowlists, contract restrictions, expiry — as an established wallet pattern, but no concrete production example beyond Safe/session-key wallets was surfaced — [coincub.com](https://coincub.com/wallets/guides/how-programmable-wallets-can-limit-autonomous-spending/), [openfort.io](https://www.openfort.io/solutions/ai-agents)
- ERC-4337 account abstraction explicitly does *not* itself provide spending limits, guardians, or session-key scoping — these must be implemented by each individual smart-wallet contract; the standard only provides the infrastructure (bundlers, UserOperations), not the risk logic — [wavect.io](https://wavect.io/blog/account-abstraction-erc4337-production/) (synthesis from search summary; primary ERC-4337 spec not directly fetched — treat as secondary-source claim)
- "On-chain prop firms" (Hypernova on Hyperliquid, Propr by XBorg/SwissBorg, Vanta, FundedHive, HyroTrader's "Hyro Protocol" on Solana) market themselves on verifiable, immutable drawdown/profit rules and on-chain payouts — [defiprime.com](https://defiprime.com/onchain-prop-firms), [hyrotrader.com](https://www.hyrotrader.com/blog/hyro-protocol-on-chain-crypto-prop-trading/)
- Critically, a close read of the defiprime.com survey found the actual trade-level enforcement mechanism is *not* publicly documented: "the routing of any single trade is not" verifiable on-chain, and the article explicitly treats whether rule-breach enforcement happens via smart-contract-level blocking vs. after-the-fact monitoring/account restriction as an open, unresolved transparency question for the category — [defiprime.com](https://defiprime.com/onchain-prop-firms)
- Hypernova is reported to enforce only a "daily payout cap" (e.g., $10K/day) as a reserve-protection mechanism — this is a withdrawal/payout limit, not a position-size, leverage, or trading circuit breaker — [defiprime.com](https://defiprime.com/onchain-prop-firms)
- Dynamic/automated circuit-breaker concepts appear in other contexts: Chainlink-style "risk oracles" are proposed to bridge off-chain volatility/liquidity/exploit signals to trigger automated pausing of smart contract operations, and some DeFi "portfolio manager" guard designs use slippage/loss-bound checks (snapshot value at open, compare at close, revert if loss exceeds a bound; track cumulative loss over rolling windows) — but these are protocol/vault-level risk controls (e.g., for an asset-management vault), not generalized "wallet can't exceed position/leverage limit regardless of which front-end signs" enforcement — [chain.link](https://chain.link/article/what-are-risk-oracles) (secondary synthesis of an unnamed "portfolio manager" design; no named shipped product identified)
- MakerDAO's Emergency Shutdown Module is cited as one of the few concretely named "DeFi circuit breaker equivalents," but it is a protocol-governance safety valve (global shutdown of the Maker system), not an individual trader's position/leverage limiter — (secondary search-summary claim; primary Maker documentation not directly fetched in this pass)

### Inferences
- The research strongly suggests that "hard, unbypassable, front-end-independent" trading-specific risk limiters (position size, leverage, circuit-breaker-on-drawdown) analogous to Safe's Allowance Module but for derivatives/perps are effectively absent from the shipped EVM product landscape as of this research. The closest shipped analogs are either (a) simple-transfer spending limits (Safe) or (b) protocol-specific vault/AMM circuit breakers that protect the protocol itself, not an individual account's trading risk.
- On-chain prop firms are the category most likely to claim this capability in marketing copy, but the one detailed third-party review found did not confirm smart-contract-level pre-trade blocking exists; it flagged the mechanism as undocumented/opaque. This is consistent with MyPropGuard's framing that most "on-chain" risk products in this space are check-then-cosign rather than enforced-at-execution.

### Gaps
- No primary documentation (whitepaper, audited contract, or technical blog) from Hypernova, Propr, Vanta, or FundedHive was fetched directly in this pass to confirm or deny their enforcement mechanism at the contract level; the defiprime.com secondary source explicitly says this is undisclosed, which is itself a meaningful finding but leaves the question technically open rather than answered.
- No hackathon (ETHGlobal etc.) prototype specifically matching "trading guardrails smart contract" or "on-chain risk limits" for position/leverage was found via search; this may reflect a real gap in attempted prior art, a search-term mismatch, or indexing limitations of the search tool used — treat as inconclusive rather than confirmed absence.

## DAO treasury Guards — what limit types are actually implemented

### Takeaway
DAO treasury tooling (Safe Guards + Zodiac Roles Modifier) is the most mature, genuinely preventive, shipped example of on-chain spending enforcement on EVM, and DAOs have implemented per-transaction caps, per-period rate/threshold limits, address allowlisting, function-level scoping, and parameter-level scoping — a materially richer rule set than Safe's basic Allowance Module.

### Cited Findings
- A Safe "Guard" is a contract the Safe calls before and after every transaction, with the ability to revert and block it — used by teams to add spending limits, transaction-source whitelists, time-of-day rules, or compliance hooks, and can be combined with Zodiac Roles "allowances" for rate limits — [onchainden.com](https://www.onchainden.com/blog/safe-wallet-review) (secondary search-summary; note this is a review/blog characterization, not the Safe/Zodiac primary spec)
- Zodiac Roles Modifier is described by its own docs as "an onchain permissions module for smart accounts" letting an entity extend transaction permissions to any address via customizable roles, implementable on nearly any existing onchain system — [docs.roles.gnosisguild.org](https://docs.roles.gnosisguild.org/)
- Per Zodiac Roles documentation, scopes for a role include: allowed target addresses; optionally, allowed functions on those addresses; allowed parameter *values* on those functions; whether delegatecall is permitted; and whether ETH value transfer is permitted — i.e., scoping goes down to individual function arguments, not just destination/amount — [docs.roles.gnosisguild.org](https://docs.roles.gnosisguild.org/) (via search summary of docs.roles.gnosisguild.org)
- Zodiac Roles "allowances" add rate/threshold limits: how frequently a role/permission can be used, and thresholds on the scoped parameters, over a given period — functionally a generalized, parameter-aware version of Safe's Allowance Module — [docs.roles.gnosisguild.org](https://docs.roles.gnosisguild.org/) / [gnosisguild.mirror.xyz](https://gnosisguild.mirror.xyz/oQcy_c62huwNkFS0cMIxXwQzrfG0ESQax8EBc_tWwwk)
- Concrete DAO usage pattern cited: an operations team can be granted a Role that lets it "pay approved vendors, but only to specified addresses, only through specified token contracts, and only up to set thresholds over a given period" — [docs.roles.gnosisguild.org](https://docs.roles.gnosisguild.org/) (as summarized by search)
- ENS DAO has gone through a "Roles Modifier V2 migration" updating its own "Endowment Permissions," indicating real, ongoing production use of Zodiac Roles by a major DAO treasury (ENS) — [discuss.ens.domains](https://discuss.ens.domains/t/ep-5-12-roles-modifier-v2-migration-updates-to-endowment-permissions/19173)
- A documented tutorial pattern ("Lower Safe Threshold for Routine Transactions") shows DAOs using Zodiac Roles specifically to let routine, bounded transactions execute with reduced signer friction while keeping the full multisig threshold for anything outside the scoped role — directly analogous to what a trading-risk product would want (unattended execution within hard bounds, full approval required outside them) — [docs.roles.gnosisguild.org](https://docs.roles.gnosisguild.org/tutorials/lower-threshold-routine-transactions)

### Inferences
- Zodiac Roles Modifier is architecturally the closest existing EVM primitive to "trading-specific limits" because it can scope on arbitrary function parameters, not just a token-transfer amount — in principle a DAO or product could define a Role scoped to a specific perp/DEX contract's "open position" function with a parameter-value cap on notional size. However, no cited source shows this parameter-scoping has actually been used for *trading* (price/size/leverage) parameters in production — documented usage is for treasury payments (destination, token, amount, frequency), not derivatives trading semantics (which require interpreting cumulative position state across multiple calls, not just bounding a single call's arguments).
- The gap between "DAO vendor-payment guard" and "trading position/leverage limiter" is state-tracking complexity: a payment guard only needs to check this call's arguments against a running spend counter; a position/leverage limiter needs running knowledge of the account's current aggregate exposure across possibly many prior calls and external price moves — which is a harder, oracle-dependent problem Zodiac Roles was not built to solve.

### Gaps
- No example was found of a DAO or product using Zodiac Roles (or any Safe Guard) to scope a derivatives/perp trading function by position size or leverage specifically, as opposed to simple token-amount treasury spending — this may not exist, or may simply not be documented/discoverable via the searches run.

## Why are hard, unbypassable, front-end-independent risk products rare?

### Takeaway
No primary-source post-mortem, team interview, or "why we built X instead of Y" piece explicitly weighing UX friction vs. oracle/P&L difficulty vs. demand vs. gas cost for trading-risk enforcement was found in this research pass. The available evidence points most directly to the oracle/state-tracking problem (option b in the prompt) as the structural blocker, with UX friction (option a) as a secondary, well-evidenced factor from the AA/smart-wallet literature; demand and gas cost are unaddressed by any source found.

### Cited Findings
- The oracle problem is described as a fundamental limitation: blockchain consensus requires deterministic, independently-verifiable computation, so smart contracts cannot natively and reliably ingest real-time external data (e.g., market prices) needed to validate position size/exposure limits; manipulated oracle data is also a correctness risk for any such check — [101blockchains.com](https://101blockchains.com/blockchain-oracle-problem/), [chain.link](https://chain.link/education/blockchain-oracles) (general oracle-problem literature, not trading-limit-specific — applied here by inference)
- ERC-4337's own documentation/ecosystem explicitly states the standard provides no built-in spending limits, guardians, or session-key scoping — that burden is pushed entirely onto individual wallet-contract implementers, which is consistent with a fragmented, mostly-simple-transfer-limit ecosystem rather than a standardized trading-risk layer — [wavect.io](https://wavect.io/blog/account-abstraction-erc4337-production/) (secondary characterization of ERC-4337)
- Safe's own Allowance Module — the most mature, widely-deployed preventive spending-limit primitive on EVM — is itself scoped to simple transfers only, by contract design (hard-coded ETH/ERC-20 transfer paths, no calldata decoding) — [github.com/safe-global/safe-modules](https://github.com/safe-global/safe-modules/tree/main/modules/allowances); this is direct evidence that even the best-resourced, most widely adopted team in this space chose the simplest enforceable surface rather than building general transaction/parameter validation.
- DeFi Saver and Instadapp, the two most prominent "position risk automation" products in DeFi, both chose a bot/keeper-reactive architecture over an enforced precondition — strongly suggesting that reacting quickly to an oracle-fed trigger was judged more tractable (or sufficient) than building a synchronous on-chain pre-trade gate that would need embedded, continuously-updated position/price state — [blog.defisaver.com](https://blog.defisaver.com/automated-strategies-technical-overview/), [guides.instadapp.io](https://guides.instadapp.io/features/protection-automation) (inference from architecture choice, not a stated rationale from either team)

### Inferences
- Taken together, the pattern across Safe (transfers only), Zodiac Roles (parameter scoping on single calls, not cumulative cross-call position state), and DeFi Saver/Instadapp (reactive bots rather than synchronous gates) suggests the dominant reason hard, preventive, trading-specific limits are rare is technical: enforcing a position/leverage/P&L limit requires a contract to know the account's current aggregate exposure and a trusted, manipulation-resistant price at the moment of each new trade, which is a genuinely harder on-chain state-and-oracle problem than bounding a single transfer's amount or a single call's named parameters. This matches option (b) in the prompt's list more than (a), (c), (d), or (e), based on available evidence — but this is an inference from observed architecture choices, not a claim any team has stated outright.
- UX friction (option a) is plausibly a compounding factor — smart contract wallets and Safe Modules/Guards still require more setup than an EOA with a normal front-end — but no source quantifies this as a reason teams avoided building trading-specific preventive limiters specifically (as opposed to smart contract wallets generally).

### Gaps
- No team interview, retrospective blog post, or conference talk explicitly explaining a decision to build reactive automation (DeFi Saver, Instadapp) instead of a preventive on-chain Guard for trading/position risk was found. This is a genuine, reportable gap: the causal "why" is inferred from architecture, not confirmed by any team's own stated reasoning.
- No source quantifying gas-cost overhead of hypothetical synchronous position/leverage checks (vs. simple transfer-amount checks) was found; cost-based rationale (option d) remains unverified either way.
- No source directly addressing market demand (option c) for trading-specific on-chain circuit breakers (e.g., customer research, VC memos, or protocol usage stats showing low adoption of any such attempted product) was found.
