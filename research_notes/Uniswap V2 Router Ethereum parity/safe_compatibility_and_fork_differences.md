# Uniswap V2 Router: Safe{Wallet} Compatibility and PancakeSwap V2 Fork Diff

## Is there documented/real-world evidence that Gnosis Safe / Safe{Wallet} can call Uniswap V2 Router functions directly?

### Takeaway
No direct primary-source evidence (a specific Etherscan transaction hash) of a Gnosis Safe proxy calling `swapExactTokensForTokens` on `UniswapV2Router02` was found in this research pass, but all available indirect evidence — the router's permissionless architecture, general Safe/DEX integration patterns, and a live GitHub issue from a Safe user about Router vs. Permit2 UX — is consistent with full compatibility and contains no indication of any EOA-only restriction. This mirrors the GMX/PancakeSwap pattern already confirmed elsewhere in this research effort.

### Cited Findings
- A live, open GitHub issue on the official `Uniswap/interface` repo, titled "Use Router instead of Permit2 for smart wallets like Safe," states: "Smart wallets like Safe can't do off-chain signatures," and describes the current UX problem as being that a Safe must (1) approve max uint256 to Permit2, (2) do a `signTypedMessage` for the swap — which becomes an on-chain transaction for a smart wallet instead of a free off-chain signature — and (3) execute the swap. The issue explicitly proposes defaulting smart wallets to "Approve tokens to Router" + "Execute the swap" as a two-step alternative, implying the Router path is both viable and already usable by Safe, just not the default UX flow Uniswap's frontend selects — [Use Router instead of Permit2 for smart wallets like Safe · Issue #6177](https://github.com/Uniswap/interface/issues/6177)
- The Uniswap DAO treasury (over $2B at various points) is itself governed by a 4-of-7 Gnosis Safe, meaning Safe multisigs are a first-class, battle-tested part of the Uniswap ecosystem's own operations (though this is treasury governance, not itself proof of a direct Router swap call) — [Bitbond: Safe(Wallet) Multisig Guide for Projects](https://www.bitbond.com/resources/gnosis-safe-multisig-guide-for-projects)
- General Safe tooling documentation (Nethereum's Gnosis Safe guide) describes the standard pattern of "one owner creates a transaction calling a DEX Router contract's swap function," confirming that calling an arbitrary router's swap function is a supported, ordinary Safe transaction type, not a special case — [Nethereum: Gnosis Safe Multi-Sig Transactions](https://docs.nethereum.com/docs/defi/guide-gnosis-safe/)
- Uniswap's own smart-contract integration docs ("Trading from a Smart Contract" / "Smart Contract Getting Started") describe the Router as a general-purpose contract meant to be called by "your contract" holding the tokens, framed generically around any caller controlling sufficient balance and router allowance — with no caller-type gating mentioned — [Uniswap Docs: Smart Contract Integration](https://docs.uniswap.org/contracts/v2/guides/smart-contract-integration/trading-from-a-smart-contract) (NOTE: this URL 301-redirects to `developers.uniswap.org`; the redirected page returned HTTP 403 to automated fetch in this session and could not be directly re-verified — flagged as unconfirmed by direct re-fetch, though the docs.uniswap.org summary was retrieved before the redirect was reported)
- Source-code review (this session, see diff section below) of `UniswapV2Router02.sol` confirms the contract contains **no `tx.origin` checks, no `msg.sender == tx.origin` gating, no EOA-only `require`, and no code-size (`extcodesize`) checks** anywhere in the six swap functions or elsewhere in the file — nothing in the bytecode-level logic distinguishes a contract caller (like a Safe proxy) from an EOA. This is a first-party confirmation from the actual source, not a secondary claim.
- Uniswap's support article "Smart Wallets and Delegation" (support.uniswap.org) could not be fetched in this session — the request returned HTTP 403 — so its content on contract-wallet compatibility is **not independently confirmed** and is omitted rather than paraphrased from a search snippet.

### Inferences
- Because `UniswapV2Router02` (and by extension any unmodified V2-style fork) uses only `msg.sender` for transfer-from/allowance checks and never inspects `tx.origin` or caller code size, there is no code-level mechanism by which it could reject a Safe proxy contract as a caller. A Safe transaction that calls `approve` on the input token (from the Safe) and then `swapExactTokensForTokens` (from the Safe) on the router would execute identically to the same calls from an EOA, from the router's perspective.
- The GitHub issue (#6177) is particularly strong secondary evidence because it is a real Safe user describing their actual current experience interacting with Uniswap's frontend using a Safe — they are not reporting a failure to call the Router, only reporting that the default Permit2-based signature flow is inconvenient for a contract wallet and asking for the simpler Router-approval flow to be offered instead. This strongly implies calling the Router directly already works for Safe users today (it is being requested as the *preferred* flow, not a *new capability*).

### Gaps
- No specific Etherscan transaction hash showing a known Gnosis Safe proxy contract address as the "From" address calling `swapExactTokensForTokens` (or any of the other five swap functions) on `UniswapV2Router02` (`0x7a250d5630B4cF539739dF2C5dAcb4c659F2488D`) was located. Etherscan's UI does not support searching/filtering by "caller is a Gnosis Safe proxy" through standard web search, and this session did not have on-chain explorer API access (e.g., Etherscan API key) to query the router's transaction list programmatically and cross-reference "From" addresses against known Safe proxy bytecode. This is a genuine gap — the conclusion that Safe-Router calls work is based on architectural/code-level reasoning and adjacent evidence, not a confirmed on-chain transaction.
- No official Uniswap Safe App was found in the Safe Apps marketplace (apps.safe.global) for V2 swaps specifically. The one Safe App integration found was a third-party "Universal V3 Staker" Safe App for V3 staking (explicitly "not affiliated with or endorsed by Uniswap Labs"), which is not directly relevant to V2 Router compatibility — [Medium: Stake in Uniswap V3 with a Multisig Safe](https://medium.com/coinmonks/stake-in-uniswap-v3-with-a-multisig-safe-universal-v3-staker-as-a-safe-app-e285d17f5808)
- Uniswap's support.uniswap.org article "Smart Wallets and Delegation" returned HTTP 403 to automated fetch and its content on EOA/contract-wallet distinctions is unverified in this pass.
- No forum post on gov.uniswap.org specifically addressing Safe/multisig Router compatibility was found or searched directly (not reached within tool-call budget for this pass).

## Does Uniswap's documentation or codebase mention any restriction limiting the Router to EOAs only?

### Takeaway
No restriction was found. A direct read of the full `UniswapV2Router02.sol` source (official `Uniswap/v2-periphery` GitHub repo, `master` branch) confirms there is no EOA-only gate, no `tx.origin` check, and no caller-type validation anywhere in the contract.

### Cited Findings
- Full source of `UniswapV2Router02.sol` was downloaded directly from `https://raw.githubusercontent.com/Uniswap/v2-periphery/master/contracts/UniswapV2Router02.sol` (446 lines) and inspected line-by-line in this session. It contains only: a `pragma solidity =0.6.6` version pin, an `ensure(deadline)` modifier checking `block.timestamp`, standard `TransferHelper.safeTransferFrom` calls keyed to `msg.sender`, and library calls to `UniswapV2Library`. There is no `tx.origin`, no `extcodesize`, and no `require(msg.sender == tx.origin)` anywhere in the file — [Uniswap/v2-periphery UniswapV2Router02.sol](https://github.com/Uniswap/v2-periphery/blob/master/contracts/UniswapV2Router02.sol)
- Uniswap's v2 architecture docs describe the Router as a stateless, permissionless "wrapper" contract around the core Pair contracts, with no mention of caller-identity restrictions — [Uniswap v2 Architecture — Smart Contracts](https://docs.uniswap.org/contracts/v2/concepts/protocol-overview/smart-contracts)

### Inferences
- The absence of any caller-identity check in the actual deployed logic (not just documentation) is the strongest possible confirmation: even if Uniswap's prose documentation never explicitly says "contract wallets are supported," the bytecode-level behavior settles the question, since Solidity's `msg.sender` mechanism makes no distinction between a Safe proxy and an EOA for any of these functions.

### Gaps
- None of substance — this question is answered directly from primary source code, which is the strongest possible evidence type for this claim.

## Function-by-function diff: UniswapV2Router02.sol vs. PancakeSwap's V2 Router source

### Takeaway
A full, direct line-by-line diff of the official Uniswap `v2-periphery` `UniswapV2Router02.sol` (master branch) against the official PancakeSwap `pancake-swap-periphery` `PancakeRouter.sol` (master branch) shows the files are **functionally and structurally identical** — same 446 lines, same Solidity pragma (`=0.6.6`), same function bodies, same order of operations, same modifiers, same control flow, same `ensure(deadline)` deadline-enforcement pattern, same fee-on-transfer balance-delta logic. The **only** differences across the entire file are cosmetic renames: `UniswapV2Factory`→`PancakeFactory`, `UniswapV2Pair`→`PancakePair`, `UniswapV2Library`→`PancakeLibrary`, `UniswapV2Router02`→`PancakeRouter`, and the revert-reason string prefixes (`'UniswapV2Router: ...'`→`'PancakeRouter: ...'`). No added safety checks, no removed checks, no fee logic differences, no event-emission differences (the router itself emits no events in either version — only the underlying Pair contracts do), no differing library/factory wiring logic (both resolve factory/pair addresses the same way via the analogous library's `pairFor`/`getReserves`/`quote`/`getAmountOut`/`getAmountsOut`/`getAmountsIn` functions), and no compiler-version difference.

### Cited Findings
- Both files were fetched directly as raw source from their official GitHub repositories in this session (not summarized by an intermediary) and diffed with Unix `diff -u`:
  - Uniswap: `https://raw.githubusercontent.com/Uniswap/v2-periphery/master/contracts/UniswapV2Router02.sol` (446 lines)
  - PancakeSwap: `https://raw.githubusercontent.com/pancakeswap/pancake-swap-periphery/master/contracts/PancakeRouter.sol` (446 lines)
- The diff output (captured directly in this session) shows every single changed line falls into one of these categories only:
  1. Import paths: `IUniswapV2Factory.sol`→`IPancakeFactory.sol`, `IUniswapV2Router02.sol`→`IPancakeRouter02.sol`, `UniswapV2Library.sol`→`PancakeLibrary.sol`
  2. Contract/interface/library identifier renames: `UniswapV2Router02`→`PancakeRouter`, `IUniswapV2Factory`→`IPancakeFactory`, `IUniswapV2Pair`→`IPancakePair`, `UniswapV2Library`→`PancakeLibrary`
  3. Revert string prefixes only (e.g., `'UniswapV2Router: EXPIRED'`→`'PancakeRouter: EXPIRED'`, `'UniswapV2Router: INSUFFICIENT_B_AMOUNT'`→`'PancakeRouter: INSUFFICIENT_B_AMOUNT'`, and all other revert reasons across every function) — [Uniswap/v2-periphery](https://github.com/Uniswap/v2-periphery/blob/master/contracts/UniswapV2Router02.sol); [pancakeswap/pancake-swap-periphery PancakeRouter.sol](https://github.com/pancakeswap/pancake-swap-periphery/blob/master/contracts/PancakeRouter.sol)
- Both files begin with the identical `pragma solidity =0.6.6;` compiler version pin — confirmed by direct inspection of both downloaded files, not a secondary summary.
- Earlier web search surfaced a corroborating secondary claim: "IUniswapV2Router02.sol is essentially the same as IPancakeRouter02.sol, with the only difference being the naming," and that the PancakeSwap fork PR primarily involved "replacing Uniswap v2-core interfaces with pancake-swap-core interfaces and fixing PancakeRouter02 naming" — consistent with and corroborated by this session's own direct diff — [pancake-swap-periphery PR #10 diff](https://github.com/pancakeswap/pancake-swap-periphery/pull/10/files)

### Inferences
- Because all six swap functions named in the research scope (`swapExactTokensForTokens`, `swapExactTokensForTokensSupportingFeeOnTransferTokens`, `swapExactETHForTokens`, `swapExactETHForTokensSupportingFeeOnTransferTokens`, `swapExactTokensForETH`, `swapExactTokensForETHSupportingFeeOnTransferTokens`) are present in the diffed region and show zero logic differences, any conclusion reached about Uniswap V2 Router's Safe-compatibility (see above) applies identically and with equal confidence to PancakeSwap's V2 Router, purely on code-identity grounds — independent of the GMX/PancakeSwap-specific confirmation already established elsewhere in this research effort.
- Since the router never emits its own events and never hard-codes a factory/WETH address (both are set once as `immutable` in the constructor and supplied at deployment), there is no possible "wiring" difference between the two forks' deployed router logic — any factory/WETH address difference is a deployment-time parameter, not a code behavior difference, and does not affect caller-type (EOA vs. Safe) compatibility.

### Gaps
- This diff compares the GitHub `master` branch source of both projects, not a byte-for-byte diff of the **verified source as published on BscScan** for the live deployed contract at `0x10ED43C718714eb63d5aA57B78B54704E256024E`. An attempt to fetch BscScan's contract-source page for that address in this session returned HTTP 403 (blocked for automated fetch), so it was **not possible to independently confirm** that the currently deployed bytecode at that exact address matches this GitHub master-branch source verbatim (e.g., if PancakeSwap deployed from a slightly different commit/tag than `master` HEAD, or applied any deployment-specific patch). Given the context note that this address is a "known fork... with these confirmed functions" and matching signatures, this is treated as very likely but is explicitly flagged as not independently re-verified against the live verified bytecode in this session.
- No GitHub tag/release/commit-hash pinning was checked — the diff used whatever commit is currently on `master` for both repos at the time of this research (2026-10-01), not a specific audited release tag. If either repo's `master` has diverged from its historically audited/deployed version, this diff would not reflect that. Not independently confirmed.

## Known behavioral quirks, bugs, or advisories relevant to smart-contract-wallet callers

### Takeaway
No Uniswap V2 Router or PancakeSwap V2 Router advisory specific to smart-contract-wallet callers was found. The only caller-relevant mechanical consideration identified is the general ERC-20 two-step approve-then-swap pattern (standard for any caller, EOA or contract) and the `deadline` parameter, neither of which differs in any way based on caller type.

### Cited Findings
- The `ensure(deadline)` modifier in both routers reverts with `EXPIRED` if `deadline < block.timestamp` at execution time — a caller (Safe or EOA) must set a sufficiently future deadline; because Safe multisig transactions can take longer to collect signatures/confirmations than a single EOA signature, a short deadline window could cause a Safe-proposed swap transaction to expire before all required signers confirm it. This is a practical UX consideration but not a code bug or restriction — inferred directly from the `ensure` modifier logic in the diffed source, not from an external advisory (flagged as an inference, not a documented advisory).
- Uniswap's own smart-contract integration docs emphasize that the calling contract/account must pre-approve the router for the input token and hold sufficient balance before calling swap functions — a universal requirement for any caller type, not specific to EOAs or contracts — [Uniswap Docs: Smart Contract Integration Quick Start](https://docs.uniswap.org/contracts/v2/guides/smart-contract-integration/quick-start)

### Inferences
- The `deadline`-expiry interaction with multisig confirmation latency is the only caller-type-adjacent "quirk" surfaced by this research, and it is a general multisig-UX consideration rather than a Router-specific bug — it applies equally to Uniswap's and PancakeSwap's V2 routers since the `ensure` modifier logic is byte-identical between them.

### Gaps
- No security advisory, audit finding, or forum post specifically discussing reentrancy, approval-pattern pitfalls, or deadline-handling problems unique to smart-contract-wallet callers (as opposed to EOAs) was found for either router in the time/tool-call budget available. This appears to be because no such caller-specific issue exists for this contract design (the Router holds no persistent token balances between external calls in the swap functions, aside from transient WETH wrapping/unwrapping within a single transaction), but this is an inference from code review, not a confirmed absence from an authoritative advisory database (no CertiK/OpenZeppelin/ConsenSys Diligence audit report was directly consulted in this pass).
