# Uniswap's V2 router matches PancakeSwap's exactly

Uniswap's `UniswapV2Router02` on Ethereum mainnet is interface-identical to PancakeSwap's V2 router on BSC, which means the Safe Guard contract built for the PancakeSwap router can be ported to Ethereum with nothing more than an address and revert-string swap. The live, verified contract sits at `0x7a250d5630B4cF539739dF2C5dAcb4c659F2488D` ([Etherscan](https://etherscan.io/address/0x7a250d5630B4cF539739dF2C5dAcb4c659F2488d#code)), has never been redeployed or migrated since it went live on **June 5, 2020** ([Etherscan tx](https://etherscan.io/tx/0x4fc1580e7f66c58b7c26881cce0aab9c3509afe6e507527f30566fbf8039bcd0)), and a direct line-by-line read of its GitHub source confirms all six target swap functions carry the same parameter types, order, and payability as PancakeSwap's router, with **zero `tx.origin` checks, multicall wrappers, or EOA-only gating** anywhere in the contract. A full diff of the two routers' official GitHub source shows the only differences across all 446 lines are cosmetic — factory/library identifier renames and revert-string prefixes (`UniswapV2Router: ...` vs `PancakeRouter: ...`) — with no logic, safety-check, or control-flow divergence. Combined with the canonical WETH address `0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2` and strong circumstantial evidence that Safe-controlled contracts already route swaps through the Router (not just Permit2), this gives high confidence that an equivalent Guard built for PancakeSwap's router will behave identically against Uniswap's, with the main residual risk being an unverified byte-for-byte check of the *live deployed bytecode* at either address against the GitHub `master` source.

## The router address has been fixed for six years, unlike GMX's rotating router

Both Etherscan and Uniswap's own developer docs independently agree on the exact same address for the production router — `0x7a250d5630B4cF539739dF2C5dAcb4c659F2488D` — verified as an "Exact Match" contract named `UniswapV2Router02`, compiled with `solc v0.6.6+commit.6c089d02` ([Etherscan](https://etherscan.io/address/0x7a250d5630B4cF539739dF2C5dAcb4c659F2488d#code)). The contract was created in a deployment transaction dated June 5, 2020 at block 10,207,858, and Uniswap's current docs still point to this same address over six years later ([Uniswap V2 Deployments](https://developers.uniswap.org/docs/protocols/v2/deployments.md)) — no redeployment, migration, or deprecation of this specific address was found anywhere. This stability is architecturally guaranteed, not just a historical accident: the router is a stateless periphery contract with no owner, no proxy, and no upgrade mechanism, so there is no code path by which Uniswap *could* silently rotate it even if it wanted to. The only prior "router change" in Uniswap V2's history was the one-time `Router01` → `Router02` upgrade back in 2020, when the older, buggy `Router01` (deployed at `0xf164fC0Ec4E93095b804a4795bBe1e041497b92a`, since deprecated for mishandling fee-on-transfer tokens) was superseded once and never touched again. This is a sharp contrast to GMX's router, which has rotated addresses across versions, and it means a Guard contract hard-coding `0x7a250d...2488D` does not carry the same obsolescence risk that a GMX-router-based Guard would.

## Six swap functions match PancakeSwap byte-for-byte in signature and logic

Direct inspection of `contracts/UniswapV2Router02.sol` on the `Uniswap/v2-periphery` GitHub repo confirms every one of the six target functions exists with identical parameter types and order to the objective's specification ([GitHub raw source](https://raw.githubusercontent.com/Uniswap/v2-periphery/master/contracts/UniswapV2Router02.sol)): `swapExactTokensForTokens(uint256,uint256,address[],address,uint256)`, `swapExactTokensForTokensSupportingFeeOnTransferTokens` (same signature), `swapExactETHForTokens(uint256,address[],address,uint256)` and its fee-on-transfer variant (both correctly marked `payable`), and `swapExactTokensForETH(uint256,uint256,address[],address,uint256)` and its fee-on-transfer variant (both correctly non-payable). A full diff against PancakeSwap's official `pancake-swap-periphery` repo (`PancakeRouter.sol`, also 446 lines, same `pragma solidity =0.6.6`) shows these six functions — and in fact the entire file — differ from Uniswap's only in **identifier renames** (`UniswapV2Factory`→`PancakeFactory`, `UniswapV2Pair`→`PancakePair`, `UniswapV2Library`→`PancakeLibrary`, `UniswapV2Router02`→`PancakeRouter`) and **revert-string prefixes** (`'UniswapV2Router: EXPIRED'` vs `'PancakeRouter: EXPIRED'`, and equivalently for every other revert reason). There is no added or removed safety check, no fee-logic difference, no event-emission difference (neither router emits events itself — only the underlying Pair contracts do), and no compiler-version mismatch. Because neither router hard-codes its factory or WETH address in code (both are set once as `immutable` constructor parameters), the only real "difference" between the two deployments is the deployment-time parameter values, not router behavior — meaning a Guard that decodes calldata against the six function selectors will produce identical decoded results whether it's pointed at the Ethereum or BSC router.

One caveat on rigor: this diff compares GitHub's `master` branch of both repos, not a byte-for-byte comparison against the live *verified bytecode* on Etherscan/BscScan for the specific deployed addresses. The BscScan page for PancakeSwap's router returned an HTTP 403 to automated fetch and could not be independently re-verified in this pass, so there is a small residual possibility (treated as low-probability, not zero) that either project's live deployment diverged from current `master` at deploy time.

## No tx.origin check exists anywhere — the router cannot distinguish a Safe from an EOA

A full-text search of `UniswapV2Router02.sol` and the `UniswapV2Library.sol` it depends on turned up zero occurrences of `tx.origin`, zero `extcodesize`-based caller checks, and zero EOA-only `require` statements anywhere in either file ([GitHub raw source](https://raw.githubusercontent.com/Uniswap/v2-periphery/master/contracts/UniswapV2Router02.sol)). The contract's only custom modifier, `ensure(uint deadline)`, checks nothing but `block.timestamp`; its sole inherited parent is the pure interface `IUniswapV2Router02`, which by Solidity's own semantics cannot contain executable logic, let alone a hidden caller-type gate. Every authorization check in the router runs through `msg.sender` (e.g., `TransferHelper.safeTransferFrom(path[0], msg.sender, ...)`), which Solidity makes no distinction on between an EOA and a contract such as a Gnosis Safe proxy. There is also no `multicall` function or batching wrapper of any kind — V2's router predates that pattern, which Uniswap only introduced in V3's periphery. This is the single strongest fact supporting Safe compatibility: it is not an inference from documentation or community reports, it is a direct reading of the only code path that could possibly block a smart-contract-wallet caller, and that path does not exist.

## Safe-Router compatibility rests on strong circumstantial evidence, not a confirmed on-chain transaction

No specific Etherscan transaction was located showing a known Gnosis Safe proxy address as the "From" field on a call to `swapExactTokensForTokens` — Etherscan's UI doesn't support filtering by caller-contract-type through ordinary search, and this research had no Etherscan API access to query programmatically. In the absence of that direct proof, the evidence is nonetheless consistent and points one direction. A live, open GitHub issue on Uniswap's own frontend repo, titled "Use Router instead of Permit2 for smart wallets like Safe," has a Safe user describing their actual current friction: Safe wallets "can't do off-chain signatures," so the default Permit2 flow forces an on-chain `approve` plus an on-chain-cost `signTypedMessage` step, and the issue explicitly proposes defaulting smart wallets to the simpler "approve to Router, then execute swap" path instead ([GitHub issue #6177](https://github.com/Uniswap/interface/issues/6177)). Critically, this user is not reporting that calling the Router *fails* for a Safe — they're asking for the Router-based flow to be made the *default*, which only makes sense if calling the Router from a Safe already works today. Separately, Uniswap's own DAO treasury (historically over $2B) is governed by a 4-of-7 Gnosis Safe ([Bitbond Safe Multisig Guide](https://www.bitbond.com/resources/gnosis-safe-multisig-guide-for-projects)), and general Safe tooling documentation treats "create a transaction calling a DEX router's swap function" as an ordinary, unremarkable Safe transaction pattern ([Nethereum Gnosis Safe guide](https://docs.nethereum.com/docs/defi/guide-gnosis-safe/)). None of this is a smoking-gun transaction hash, but combined with the code-level absence of any caller-type check, there is no credible mechanism by which the router could reject a Safe as caller, and no report anywhere suggesting it does.

## WETH address is fixed and shared across the DeFi ecosystem

The canonical WETH9 contract on Ethereum mainnet is `0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2`, verified on Etherscan as "Wrapped Ether" with 18 decimals and standard `deposit()`/`withdraw()` wrapping functions ([Etherscan: Wrapped Ether](https://etherscan.io/token/0xc02aaa39b223fe8d0a0e5c4f27ead9083c756cc2)). `UniswapV2Router02`'s constructor takes this address as an immutable `_WETH` parameter (exposed via a public `WETH()` getter), and because the router has never been redeployed, that value has never changed since 2020. The one piece of rigor not fully closed here is that the raw constructor-argument hex for `_WETH` was not independently decoded byte-for-byte from Etherscan in this research pass — the identity rests on Uniswap's own documentation and universal ecosystem convention rather than a raw constructor-calldata read, though no contrary evidence of any kind was found.

## Conclusion

The practical upshot for porting a Safe Guard contract from PancakeSwap to Uniswap V2 is that essentially nothing about the Guard's decoding or validation logic needs to change — only two constants (router address and WETH address) need updating, since the function selectors, parameter layouts, and the absence of caller-type checks are identical across both deployments. The two meaningful gaps worth closing before shipping — neither of which changes the conclusion but both of which are cheap to close — are (1) confirming the live BscScan-verified bytecode for PancakeSwap's router matches the GitHub `master` diffed here (the BscScan fetch was blocked by a 403 in this pass), and (2) locating one concrete on-chain transaction of a Gnosis Safe proxy successfully calling `swapExactTokensForTokens` on Uniswap's router, which would convert the current strong circumstantial case into direct proof. Neither gap suggests any reason for doubt; they are closure items, not red flags.
